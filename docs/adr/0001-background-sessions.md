# ADR-0001：后台续跑 / 多会话架构（issue #6）

日期：2026-08-04 · 状态：提议（实施中的部分已标注）

## 背景

issue #6 要求：切走的会话继续在后台推进，回来时能接上进度；并讨论是否需要标签页/多会话架构。

## 现状盘点（先承认已有的）

当前架构其实已经具备后台续跑的骨架，问题出在细节而不是缺架构：

- **单 ACP client 多路复用**：`KimiBackend` 用一个 `kimi acp` 子进程承载多个会话（acpSessionId ↔ bridgeSessionId 映射），会话切走后 turn 并不中断。
- **后台缓冲**：`sessionStore.backgroundSessions` 为每个切走的会话维护离屏 items 缓冲，流式事件继续折入；切回走 attach 路径直接接管缓冲（软上限 12 / 硬上限 24）。
- **托盘通知**：后台会话完成后已有原生通知。

也就是说"后台续跑"已经是事实；用户感知到"切走就停了"的原因是三类缺陷：

1. 瞬时 UI 状态（子代理面板、权限请求、待办）不进缓冲快照 → 切回后计数全错（#23）。
2. 运行状态不可见：侧栏没有运行中标识、输入区忙碌无原因（#5）。
3. 流式批处理队列在切换时的乱序/幽灵气泡问题让切回体验看起来是坏的。

以上三条均已在 2026-08-04 的修复批次中处理。

## 决策

**不引入标签页/多窗口，也不做每会话独立进程。** 理由：

- 单 ACP 进程约 300MB 内存，每会话一个进程在多会话场景下不可接受；
- Kimi CLI 的 ACP 实现本身支持单进程多会话，多进程反而绕开了它的会话管理；
- 标签页解决的是"并行盯着看"，而 Tran 的用户模型是"一个前台会话 + N 个后台推进"，侧栏运行标识 + 托盘通知已覆盖该需求，成本低一个量级。

**强化现有单进程多会话模型**，按序推进：

1. ✅ 瞬时状态入快照（#23）——运行计数/计时/权限请求随缓冲折叠与恢复。
2. ✅ 运行状态可视化（#5）——`runningSdkSessionIds` + 侧栏标识 + 输入区忙碌原因。
3. ✅ ACP 进程崩溃自动恢复（#3）——client 重建 + session/load resume + 保留已输出内容。
4. 待做：重启应用后恢复"进行中"标识——启动时查 `~/.kimi-code` 磁盘任务记录（kimiServerApi.readDiskTasks 已有数据源），把仍在 running 的会话标出来。
5. 待做（可选）：后台会话的轻量"画中画"预览（悬停侧栏项时显示最近一条输出），替代标签页的"瞟一眼"需求。

## 后果

- 内存与进程模型不变，无新增常驻开销。
- 若未来确需并行盯多个会话，再评估拆分窗口（Electron 多 BrowserWindow 共享主进程状态）而不是标签页——那时本 ADR 需要修订。

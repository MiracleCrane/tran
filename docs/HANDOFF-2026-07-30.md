## 3. 下一步（按优先级）

### 3.1 【最高】接 kimi 本地 server 的 WebSocket，让待办即时更新

**这是用户反复提的痛点：「待办更新总是不及时，或者一直就不更新了」。**

根因是两层，第一层已修（`45c61b7` 的多会话轮询），第二层是架构性的：
**待办只有模型跑 turn 时才会写**（见 4.5）。

已经查明的可用接口（拆 `@moonshot-ai/kimi-code` 的 bundle 得到，见 4.4）：

| 接口 | 给什么 |
|---|---|
| `GET /sessions/{id}/transcript` | 响应里直接带 **`todos`**——待办真值，零 token |
| `GET /sessions/{id}/transcript/ops?since_seq=N` | 增量 op 流：`todo.upsert` / `task.upsert` / `plan.*`，按 seq 续传。**GET only，不能写** |
| `ws://127.0.0.1:<port>/api/v1/ws` | **推送**。`event.session.work_changed`（带 `busy` 和 `last_turn_reason`）、`status_changed`、`approval.*`、`question.*`、`fs.changed`、`goal.updated`。带 `{seq, epoch}` 水位线和断线重放 |
| `POST /sessions/{id}/prompts::steer` | 往**正在跑的** turn 里插话 |

鉴权：WS 用子协议 `kimi-code.bearer.<token>`，token 来自
`~/.kimi-code/server.token`——`src/main/kimiServerApi.ts` 已经在读了，端口发现
（`~/.kimi-code/server/instances/*.json`）也已经实现，直接复用。

**实施建议**：新建 `src/main/kimiEventStream.ts`，用 Node 22 的全局 `WebSocket`
（**不要加 `ws` 依赖**，见 4.6）。做完之后：

1. 待办/任务读的是真值，不再依赖 ACP 流里恰好出现的 plan 帧
2. 所有会话（含后台）同时被观察，`45c61b7` 的轮询可以退化成兜底
3. `event.session.work_changed` 的 `busy` 转 false 是"turn 结束"的可靠信号

**剩下的硬缺口**：待办内容要真的推进，必须有一次 turn。用户明确说
「不想我来发消息」——意思是 **Tran 自动替他发**，不是"别发"。设计：

- 触发条件：后台任务已收尾 + 待办有未完成项 + 会话空闲（这三个条件
  `PlanCard.tsx` 的 `settledBackgroundTask` 已经在算了）
- 动作：发一条隐藏消息催更新，回显吞掉（Tran 已有隐藏 turn 机制，见
  master 的 `b09e119` "plan frames bypass hidden-turn swallow"）
- 门槛必须严：同一个任务只触发一次、只在空闲时、有开关、**并且在界面上标明
  「Tran 自动请求了一次待办更新」**——不能是幽灵行为

## 4. 实测确立的事实（**动手前必读**）

这一节每条都是用真实环境验证过的。**不要凭直觉推翻它们。**

### 4.1 git 的 `--` 分隔符不能一律加

给 `checkout` 加 `--` 会**改坏功能**：`git checkout -- <name>` 的语义是"从索引恢复
该路径的文件"，不是切分支（git 2.43 实测，报 `pathspec 'feature' did not match`）。
`--end-of-options` 对 `branch`/`revert` 有效，对 `checkout` 无效。

所以 `git.ts` 用的是 `assertRef()`——拒绝以 `-` 开头的 ref。
而 `add`/`reset`/`diff` 的 `--` **是安全的**（语义就是"后面全是路径"），已经加了。

只读 git 命令统一加了 `--no-optional-locks`：默认的 `git status` 会顺手**写**索引，
Tran 在旁边轮询就是在和 agent 自己跑的 git 抢 `index.lock`。

### 4.2 Claude Code 的 stream-json 帧（v2.1.220 实测）

一开始有五处猜错了，实测后修正：

- turn 信号是 `system/status` 的 `status:"requesting"`
- `type==='user' && isReplay===true` 的帧**必须丢掉**，否则用户消息重复
- MCP 服务器列表和技能列表在 `system/init` 帧里（还有 `commands_changed`）
- 上下文窗口从 `result.modelUsage.<model>.contextWindow` 取，实测
  claude-sonnet-5 是 **1_000_000**，不是 200k
- `result` 帧**没有** `totalTokens` 字段
- `rate_limit_event` **只给窗口类型和重置时刻，不给已用量/上限**——所以额度环
  对这些窗口显示"无数据"，不编造百分比。这是与 kimi 后端的实质差距

还有一个坑：合成的 `system/plan_usage` 消息**推不到渲染层**——额度环走的是 IPC
拉取（`forge:getPlanUsage`）而不是消息通道。已改成后端留存 + 按后端路由。

### 4.3 两个 permission 枚举不一样，别混

| 位置 | 合法取值 |
|---|---|
| CLI `--permission-mode` | `manual` / `acceptEdits` / `auto` / `bypassPermissions` / `dontAsk` / `plan` —— **没有 `default`** |
| settings.json `permissions.defaultMode` | `default` / `acceptEdits` / `auto` / `bypassPermissions` / `dontAsk` / `plan` —— **没有 `manual`** |

（`claude --help` 与二进制内的枚举表实证。）配置文件的 `default` 等于命令行的
`manual`，都是"每次询问"。Tran 的 `PERMISSION_MODE_MAP` 映射到 `manual`，是对的。

另一条二进制内的原文约束：`"defaultMode": "auto"` **必须写在用户级文件**，
写在项目 `.claude/settings.json` 里会被当作"仓库可控"而**忽略**。

`--print` 非交互模式下**没有交互授权通道**（没观察到 `--permission-prompt-tool`，
也没有权限帧）。所以 Tran 的 Claude 后端靠的是 `--permission-mode` + settings 规则
提前配好，不是弹窗。**交互式 CLI 里则会正常弹窗**，`permissions.ask` 那条路只在
交互模式下有意义。

### 4.5 待办为什么不会自己更新

```js
TodoModel = defineCheckpointedModel("todo", () => [])
TODO_LIST_REMINDER_TURNS_SINCE_WRITE = 10        // 10 轮没写就提醒模型
TODO_LIST_REMINDER_TURNS_BETWEEN_REMINDERS = 10
```

待办是 checkpointed model，**只有模型调 todo_list 工具时才变**。kimi 自己都知道
模型会忘，所以内置了催更新的提醒机制——而它也是**按 turn 计的**。

`transcript/ops` 是 GET only，所以"绕过模型直接改待办"这条路不通。就算通我也不建议：
伪造 agent 状态，用户很快就不信这个面板了。

会话状态落盘在 `~/.kimi-code/sessions/wd_*/<sessionId>/`：
`agents/main/wire.jsonl` 是 op 日志（`todo.upsert` / `task.upsert` / `context.append_message`），
`state.json` 有 `lastPrompt`。


### 4.7 便宜模型的实测数据

> ⚠️ **这一节 2026-07-30 晚被重测推翻过一次。** 下面是修正后的版本，
> 被推翻的原文见本节末尾——留着是因为**怎么错的**比结论本身更值得记。

#### 型号存在性只能问 `/models`

`GET https://api.kimi.com/coding/v1/models`（同一套 Bearer）返回权威目录，
实测**只有四个**：

| id | display_name | context_length |
|---|---|---|
| `kimi-for-coding` | K2.7 Coding | 262144 |
| `kimi-for-coding-highspeed` | K2.7 Coding Highspeed | 262144 |
| `k3` | K3 | 1048576（支持 `think_efforts`: low/high/max） |
| `k3-256k` | K3-256k | 262144 |

**chat 端点完全不校验 `model` 值**：随便写什么都回 200，并把这个值原样回声在
`response.model` 里。实测连 `gpt-4o` 和现编的 `zzz-not-a-real-model-20260730`
都"通"。→ **"打得通"不能证明型号存在。**

回落到哪个也是可测的：虚构 id 的 `prompt_tokens` = 82，与 `kimi-for-coding`
一致；k3 系是 134/137（系统预置不同）。即虚构 id 落到的就是 `kimi-for-coding`。

#### 延迟（真实 id，正确提示词，3 发热连接）

```
                          第一轮(min/中位)   第二轮(min/中位)
kimi-for-coding             844 /  885        967 /  971    ← 保持默认
kimi-for-coding-highspeed  1080 / 1098        791 /  990
k3                         1160 / 1237       1107 / 1147
k3-256k                    5007 / 5547       1373 / 2052    ← 抖得厉害
```

两轮之间 `kimi-for-coding` 和 highspeed 互换了名次，差值也就一两百毫秒——
**这两个在这个任务上分不出快慢，别拿它当选型依据**。`k3-256k` 两轮差了 3 倍，
是唯一确定有尾延迟风险的。k3 系的 `prompt_tokens` 是 134/137 而 for-coding 系是
82，说明服务端给它们的系统预置不同。

比早前记的 1.7~1.8s 快了一倍，**不是网络变好了**：早前 `outTok` 恒等于
`max_tokens`，说明模型每发都在写长文写到被截断，延迟是被"生成 N 个 token"撑起
来的。提示词修好后输出只有 4~16 个 token，延迟自然掉下来。
→ **「1.7s 延迟是硬伤」这个结论作废**，但"不阻塞 UI、结果要缓存"仍然照做。

#### 指令遵循：三道防线之后是合格的

踩过两层：

1. 裸提示词（只在 system 里写"只输出结果、不超过 12 字"）→ 全部无视，
   一律写 markdown 长文然后被 `max_tokens` 截断
2. 把少样本写成纯文本塞进**单条 user 消息** → **答非所问**：模型把整段当成
   "一堆待处理内容"，抓住**第一个示例**当主题。实际输入
   `npm run build && ...` 得到的是关于 `git status --porcelain` 的表格；
   命名任务里三个不同输入全都回答示例里的"401 排查"

改成真正的多轮 `user`/`assistant` 轮次 + `stop` + 输出侧 `terseText()` 之后，
**12 条不同命令 12 条全对且全在 12 字内**（`kimi-for-coding` 与 highspeed 各 6 条）：

```
npm run build                                → 构建项目
kubectl rollout restart deploy/api -n prod   → 重启生产环境API部署
rm -rf node_modules && npm ci                → 删除依赖并重新安装
curl -s http://jenkins/.../api/json          → 获取Jenkins构建信息
ssh deploy@10.0.0.5 "systemctl restart nginx" → 重启远程服务器 nginx
grep -rn "TODO" src/ | wc -l                 → 统计TODO数量
```

#### 两个必须原样保留的参数

- `thinking: { type: 'disabled' }` 是**载重参数，不是优化**。目录里四个型号全是
  `supports_thinking_type: "only"`；把这个字段整个去掉，`max_tokens=36` 的预算
  会被推理吃光，`content` 回**空字符串**（实测）。
- `temperature` 一律不要传：传 0 直接 400
  `invalid temperature: only 0.6 is allowed for this model`。

#### 额度

`/usages` 的 `limit` 恒为 100——那是**百分比**不是 token 数。31 发（约 2100
token）两个窗口的 `used` 都没动，**只说明低于计数器分辨率，不能解读为不计费**。

#### 被推翻的原文，以及怎么错的

> **"极速版"没有可测的优势**——除 k3 外全在 1.7~1.8s，差异在噪声里。
> （kimi-for-coding 1813 / kimi-k2.6 1784 / kimi-k2.6-turbo 1707 /
> kimi-k2.7-code 1693 / kimi-k2.7-code-turbo 1817 / kimi-k3 2951）

那六个名字里**五个不存在**，服务端静默回落到 `kimi-for-coding`。所以这份基准
是**把同一个型号测了六遍**——"差异在噪声里"当然成立，因为本来就是同一个东西。
两个独立的错误正好互相掩护：型号名是手写猜的（没有任何来源），而端点又对错误
的型号名保持沉默。

**教训**：探测"能不能打通"永远不能替代"存不存在"。凡是服务端有目录接口的，
先拉目录。

### 4.10 两条凭证链，以及「用 2.6 就不计 Code 额度」这个说法的真相

Tran 里**已经有两条独立的 Kimi 凭证链**，别只记得第一条：

| | 凭证来源 | 端点 | 用途 |
|---|---|---|---|
| A `usageService.ts` | `~/.kimi-code/credentials/kimi-code.json` | `api.kimi.com/coding/v1/*` | 主 agent、额度环、**全部总结类小请求** |
| B `quotaService.ts` | **kimi-desktop 的** `%APPDATA%/kimi-desktop/bridge-store/token-store.json` | `www.kimi.com/apiv2/…MembershipService` | 额度明细（总览 + 使用流水） |

B 那条已经做得很完整：读桌面版 token → 过期用 refresh_token 换新写回 → 还有
BrowserWindow 登录兜底（从 localStorage 提 JWT）。**但它只接了 membership RPC
（读额度），没有对话端点。**

#### 「2.6 不计入 Kimi Code 额度」——半对

2026-07-30 用 B 链读的真实数据：

```
ratelimitCode5h   ratio 0.0805  enabled
ratelimitCode7d   ratio 0.6091  enabled
ratelimit5h/7d    不存在（这个账号没有独立的通用限速窗）
subscriptionBalance {
  feature: FEATURE_OMNI, unit: UNIT_CREDIT,
  amountUsedRatio:   0.4921,   ← 订阅总用量
  kimiCodeUsedRatio: 0.3323    ← 其中 Kimi Code 占的部分
}
```

Code 有自己的 5h/7d 限速窗，网页版对话不占这两个窗口。

> ⚠️ **我在这里推断错过一次，留下来当教训。**
> 我曾从字段名推断：`amountUsedRatio`(0.4921) 和 `kimiCodeUsedRatio`(0.3323) 都挂在
> 同一个 `subscriptionBalance` 下、同一个 UNIT_CREDIT，所以「非 Code 用量 ≈ 16%
> 出自同一个池子，换 2.6 不是免费只是记在另一个口径」。**这是错的。**
> 用户说 2.6 不计费，我拿字段语义的直读去反驳他——而这个问题**根本不需要推断，
> 流水里有答案**。

#### 真相：网页对话确实不计费（`ListBalanceActions` 实测）

翻 500 条流水（25 页）按 feature 汇总 `amountRatio`：

```
FEATURE_CODING     456 条   合计 0.0538   单条最大 0.0026（待办催更那一轮）
FEATURE_AGENT (k3)   6 条   合计 0.0009
FEATURE_WEBSITES     1 条   合计 0.0003
FEATURE_CHAT        37 条   合计 0.0000   ← 每一条都是 0
     标题就是网页版的会话名："k2.6: Codex 与克劳德 (27)" …
```

**FEATURE_CHAT 37 条无一例外扣 0。** 网页对话是真免费。

⚠️ 汇总时注意：条目里 `amount` 字段是**空的**，真实值在 `amountRatio`。按 `amount`
求和会得到一片 0，看起来"什么都不花钱"——我第一遍就是这么错的。

#### 结论：总结类**要**搬到网页通道（已实现，见 `kimiWebChat.ts`）

A/B 实测坐实（同一天 07:05 vs 07:08）：走网页通道打 4 发，流水里**没有**对应的
扣费簇；强制切回 code 通道打 2 发，07:08:21 和 07:08:23 立刻出现一对紧挨着的
0.0001，打断了原本 40~70s 一条的背景节奏。

但**待办催更搬不了**（见 4.11）——它必须发生在那个 kimi 会话里。这两件事要分开看：
不是"总结类也搬不动"，是"待办这件事本身外包不掉"。

### 4.11 待办催更为什么贵，以及为什么外包不掉

催更是一次**完整 turn**，要把整个会话上下文重新过一遍。实测被催的那个会话：
transcript 42 条记录、序列化 221472 字符 ≈ **88000 token**。同一批功能里的小请求
（命名 / 命令说明 / 思考摘要）各约 120 token——**差七百倍**。

而且它买到的比看上去小：kimi 的后台任务完成通知本来就在**下一轮**注入上下文，
用户下次随便发条消息待办自己就会更新。催更买到的是「提前」，不是「否则不更新」。
→ 所以 `autoTodoNudge` **默认关**。

外包给便宜模型/别的账号——**做不到，跟额度无关**：待办是 checkpointed model，
唯一的写入者是会话自己的 agent 调 `todo_list`。kimi 二进制里 todo 相关只有
`todoListTool` 和只读的 `transcript/ops`，**没有任何 HTTP 写路由**。外部模型写不
进去；就算写进去，面板和 agent 自己的认知也会对不上，那是伪造 agent 状态。

### 4.8 元素类型不能随状态变化（踩过两次）

React 按位置比对元素类型，类型不同即卸载重建。这个仓库踩过两次：

1. 转圈动画被重置——`components` 对象每帧新建，Virtuoso 的 Footer 组件类型不稳定
2. 每轮输出结束整条消息 remount——文本块外面套的 `<Profiler>` 随 `isStreaming`
   出现/消失。代价：思考块的用户折叠态被丢弃（最新块会自己弹回展开）、
   正文 markdown 整树重建 + highlight.js 重跑，正好卡在用户开始读答案那一刻

顺便：`<Profiler>` 的 `onRender` 在生产构建里**根本不回调**（要
`react-dom/profiling` 才生效）。

### 4.9 一个假警报，别再报了

早前把「中文输入法按 Enter 会误发送」报成 P0。**是误判。** CDP 里合成的 Enter
事件确实匹配，但真实 Windows IME 发的是 `key:"Process"` / `keyCode:229`，走不到
那个分支。用户也确认"用了很久没遇到过"。这是**模式推断，不是验证**。
